# 事件与卡片写作指南

> SKILL.md 步骤 4 的写作参考。内容判断标准以 task_def（§2.5、§10、§15）为准，本文给出落到事件 JSON 与 Markdown 卡片上的做法。

**P2 硬约束：claim inventory（逐条论点抽取）**

一份原文常含多个独立论点。**禁止对整篇只抽一条技术命题** —— 这会让同一个
事件只保留一个叙事角度，其余论点静默消失。

每个 A / A+ 事件必须在 event JSON 中写 `claims` 数组，每项：
```json
{"claim": "一句话原文论点", "change_types": ["CT-01"], "primary_path": "C2.1",
 "disposition": "absorbed:EV-03 | separated:EV-07 | discarded:重复",
 "reason": "处置理由（discarded 必填）"}
```
- `absorbed` — 由本事件承载（写本事件编号），本事件再经 `thesis_decision` 归属命题
- `separated` — 独立成一个事件（跨层/跨命题时必须分离）
- `discarded` — 丢弃，必须写理由

典型反例：Anthropic 关于"何时把 subagent 折叠进主 loop"的文章，若只被抽象成
"Agent Skills 标准化（→ AAIF）"，就丢掉了"并行/隔离/核验场景仍需 Subagent"
这个独立的架构边界命题。这两个 claim 必须分别处置。

**P3 硬约束：同实体不同系统层不得合并**

同一 Tier-1 实体在本窗口出现 ≥2 条候选时，**先按系统层分解**，每层独立评级、
独立技术命题，**只有同层同命题才允许合并**：

| 系统层 | 典型内容 |
|---|---|
| Model | 模型能力、权重、benchmark |
| Runtime / Sandbox | agent 执行环境、沙箱、权限 |
| Platform API | API 契约、SDK、生命周期 |
| Ops / Governance | 监控、故障关联、运维 Agent |
| Hardware / Infra | 芯片、多机推理、集群 |
| Docs / DevRel | 文档、教程、发布说明 |

反例：把 OpenShell（Runtime/Sandbox）、Minerva（Ops）、Cosmos（训练/模拟）、
DGX Spark（Hardware）合并成"NVIDIA Agent 基础设施"，会让四个不同技术命题
互相吞没。它们分属四层，本就不该合并。

**主卡结构**：`####` 标题 → 评级标记行（见 SKILL.md 步骤 5 的结构契约）→ 元信息表（task_def §17 的必备字段）
→ 一段摘要 → 深拆小节。task_def §15 的分析门槛按 §15 末尾的落位写进这些位置。

**卡片标题必须是双层式** `关键词｜一句总结`（全角竖线 U+FF5C）：

- **前半**取自原始标题里的实体或关键词，照抄不转述——读者扫视时先要认出"这是谁"。
  产品/模型名、论文的核心术语、组织名都算；不要写成自己造的概括词。
- **后半**是这条事件的技术判断，一句话，不重复前半的词。

渲染器按竖线把两层分开排版（前半是强调色小字，后半是标题字号），所以竖线不是装饰，
是结构。没有竖线的标题会退化成单层渲染，门禁会拦。

| | 写法 |
|---|---|
| ✅ | `ERNIE Evolve｜双循环把研究方向搜索与可验证代码演化接成生产闭环` |
| ✅ | `SemVer 对照实验｜版本标签会改变部分编码 Agent 的检查行为` |
| ❌ | `ERNIE Evolve 将研究方向搜索与可验证代码演化接成双循环` —— 单层，扫视时认不出边界 |
| ❌ | `自动研究｜ERNIE Evolve 接成双循环` —— 前半是自造概括词，不是原始标题里的关键词 |
| ❌ | `OpenAI SDK｜增加 Agent Session 流选项，不能据此推断新调度能力` —— 后半是否定句，
      一条事件最值得说的若是它不能证明什么，它就该进附录 A而不是占事件编号 |

**卡内顺序**（2026-11-11 起）：标题 → 标记行 → 四节技术深拆（A/A+）或一段结论（B/C）→
`##### 对我们的含义`（A/A+）→ 元信息表。**元信息表放在卡片最后**：读者先要知道发生了什么，
核对时才需要出处；渲染器按表头「元信息」识别它并默认折起。

**「对我们的含义」怎么写**（A/A+ 必填，B/C 可不写）：

它是推演，不是结论先行的表态——必须建立在前面四节已经交代清楚的技术事实上。三个要求：

1. **有技术依据**：引用本卡前文的一个具体机制或数字，说明含义是从哪一点推出来的。
2. **落到具体环节**：指明它影响的是哪条技术路线的哪个环节（哪个根技术、哪种部署形态、
   哪项评测口径），而不是泛泛的"值得关注""需要跟进"。
3. **写出不成立的范围**：原文没有验证的场景（端侧、功耗、跨任务）要明说不能外推。

写成条件句与待验证项，不写成定论与行动号召。门禁会拦掉「颠覆 / 革命性 / 彻底改变 /
遥遥领先 / 必须立即」这类定性夸大用语，以及少于 60 字、排在技术深拆之前的写法。

| | 写法 |
|---|---|
| ✅ | 该接口把候选集与升级阈值留在 Harness、决策读出内化到模型。若端侧高频路由采用同类契约，需先在目标芯片上实测 100–200ms 预算是否成立；原文只给了输出契约，没有手机场景的时延与校准数据，不能据此判断可替换现有生成式路由。 |
| ❌ | 这将彻底改变端侧助手的技术路线，建议尽快跟进。——没有依据、没有环节、没有边界，且是定性夸大 |
| ❌ | 值得持续关注其后续进展。——等于没写 |
| ❌ | 对我们的记忆系统有重要参考价值。——没说是哪个机制、参考什么、在什么条件下成立 |

**标记行要带 change_object**：`**<评级> · <信号> · EV-xx · <层>**`，层取
`Model` / `Harness` / `运行平台` / `交互·应用` / `尚未披露`，与事件 JSON 一致。
渲染器按它给卡片上色，所以这不是装饰字段：读者会按颜色判断「这个变化发生在哪一层」，
写错等于让颜色说谎。层名在标记行里是可见文本，灰度打印与色觉差异下仍然可读，
颜色不是唯一载体。

**A/A+ 事件卡四维深拆硬约束**：每张 A/A+ 主卡（不只是 Top 1）必须含四个 `#####` 五级小节
（结构契约见 SKILL.md 步骤 5），缺一不成稿：

| 章节 | 内容 | 数据来源 |
|---|---|---|
| **挑战与问题** | 现有方案的三道坎（精度/速度/隔离/成本等具体痛点，不是泛泛而谈） | 原文背景段 + 技术常识 |
| **机制与架构** | 新方案如何回应这三道坎，引用原文关键设计词（如 natively multimodal / event-driven / commit-order prediction） | **必须 fetch 官方原文** |
| **效果与定量** | 原文披露的关键数字（benchmark/参数/定价/速度），抓不到就显式标"blog 未在首发时披露"，不得编造 | **必须 fetch 官方原文** |
| **对比其他方案的价值** | 横向对比 2-3 个竞品（同栏目优先），点出本方案差异化价值，回扣 TH 命题 | 原文 + 候选池同栏目事件 |

- **写卡前必须 fetch 原文**：候选池的 `snippet` 常截断到 300 字符，不要据此猜机制。arXiv 取
  `arxiv.org/abs/<id>` 的 `<blockquote class="abstract">`，厂商 blog 取 `datePublished` 与正文。
  抓原文遇企业网络拦截用华为代理 `proxyca.huawei.com:8080` + `urllib.request.ProxyHandler` 绕过；
  URL 从 `candidate_pool.json` 按 title 关键词提取，不要手编 slug。
- **B 级卡片不强制四节**，但 A/A+ 必须四节齐全；持续信号卡（附录 A）、聚合栏目摘要卡不适用。
- **无官方原文可抓的事件**：聚合源（如 Techmeme）摘要信息充分时可以支撑事件卡，但卡片上标
  "媒体摘要，未回溯原文"，并在 C.3 记根因"官方原文未回溯"。
- 四节总长 200-350 字/卡；横向对比至少 2 个竞品（1 同栏目 + 1 跨栏目）。

## 第 1 章写法

**intro 区深层推理硬约束**：

intro 区（第 1 章）不只是列举事件，必须分两层写，缺第二层不成稿：

| 层 | 元素 | 内容 |
|---|---|---|
| 事实层 | 普通段落 + Dashboard 表 | 列举 2-3 条主线各自做了什么（一句话/条）+ Dashboard（字段见 task_def §17） |
| 推理层 | `> [INSIGHT] ...` callout | 把多条主线合在一起指向什么——跨层解耦/叠加效应/工程经济学改变等**潜在价值**，不是简单复述 |

推理层写作要求：
- **不强行汇总到单一技术方案**：h1 仍是多命题并列；INSIGHT 框是"潜在价值"而非"已证实结论"。
- **必须标证据边界**：跨事件推理的因果链若未经单一来源证实，结尾写明"应视为本轮窗口内的分析假设而非已确立结论"。
- **可空但不可假**：若本轮事件间无明确跨层关系，推理层可写"本轮事件以独立信号为主，未发现跨层收敛"，
  不得强行编造因果。

## 视觉约束

**视觉侧的三条硬约束**（写 MD 时就要落实，门禁不查但必须遵守）：

| 约束 | 做法 | 违反后果 |
|---|---|---|
| 首屏即结论 | 第 1 章第一段是结论 + 一句话，不是装饰 hero | 读者 10 秒内读不到本轮判断 |
| 一图一主张 | 图用 `![结论文字](图源)`，alt 文本写结论不写"如图所示" | 图退化成装饰 |
| 数字成图 | 跨度/占比/比较用表格或本地图片（SVG/PNG），不要用纯文字罗列数字；渲染器不支持 mermaid | 数字无法比较 |
