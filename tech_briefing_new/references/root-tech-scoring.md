# 根技术计分规则（Strategic Adjacency）

> 技术简报 skill 的战略相关度依据。数据源：`data/root_tech.json`（由《小艺业务部根技术清单_26年刷新版》转换）。
> 本文件对应对比报告第 8 节第 10 条，替代原先设想的"关注领域画像"。

## 1 为什么用根技术清单，而不是另写一份关注领域

关注领域清单只能回答"这条新闻跟我们有没有关系"，模型各自理解，方差不会收敛。根技术清单里每一项都写了 **切换信号**——一个可证伪的条件，说明"出现什么证据时，投入应从当前代转向下一代"。这正好是事件价值的判据：

**一个事件值不值 A，取决于它是否构成某项根技术切换信号的证据。**

这样三个模型拿的是同一把尺子，而且这把尺子是部门已经写好的，不需要为简报另造一套价值观。

## 2 计分单位

**根技术层**（M1.1 / H5 / S2.2 这一级），共 82 项（清单 81 项 + M8 快思考模型）。
不使用技术点层：技术点随代际增删，不稳定，且粒度细于单个事件。
不使用方向层：太粗，几乎每个事件都能挂上。

另有 4 项候选根（B6.x）单列，只记录不计分，命中时写入第 5 章作为"候选根升格信号"。

## 3 计分表

| 分值 | 条件 | 判据 |
|---|---|---|
| **2** | 事件构成某项根技术 **切换信号的证据**，支持或否证皆可 | 事件改变了"当前代够不够用"的判断 |
| **1** | 事件落在某项根技术的核心或关联叶子上，是当前代的进展，但不改变代际判断 | 同方向进展、工程实现、增量发布 |
| **0** | 与任何根技术无关 | 融资、股价、评级、立法、人事、纯观点 |

**反证与支持同分。** 否证一项根技术当前代假设的事件（例如"端侧推理是浪费内存"对端侧路线），与支持证据拿同样的分。否则清单会把简报变成确认偏误的放大器。

## 4 事件 JSON 字段

```jsonc
"root_tech": [
  {"id": "RT:S2.2",                    // 必须带 RT: 前缀，见第 6 节
   "relation": "switch_evidence",      // switch_evidence | current_gen | —
   "direction": "supports",            // supports | contradicts
   "signal_quote": "语义级审查成为技能市场准入标准",   // 命中的切换信号原文
   "why": "一句话：事件如何构成该信号的证据"}
]
```

字段写在**事件 JSON 顶层**（不是 `scoring` 里面）。`scoring.strategic_adjacency.score`
必须等于 `root_tech.derive_adjacency()` 的派生值，不一致时门禁拦下——要改分就去改
`relation` 并写证据，不能直接改分数。

`scoring.validate()` 经 `root_tech.validate_hits()` 校验：

| 检查 | 失败条件 |
|---|---|
| 前缀 | `id` 不带 `RT:`（与叶子编号有 11 处重名，见第 6 节） |
| 存在性 | 去掉前缀后不在 `root_tech.json` 的 `roots` 里 |
| 候选根 | 命中 `candidates`（B6.x）——只记录不计分，应写进第 5 章 |
| 关系 | `relation` 不在 `switch_evidence` / `current_gen` |
| 方向 | `switch_evidence` 未声明 `direction ∈ supports/contradicts` |
| 信号原文 | `signal_quote` 与清单的 `switch_signal` 不逐字一致 |
| 理由 | 缺 `why` |
| 落点 | `primary_path` 不在该根的 `leaves_core ∪ leaves_related`，且 `why` 里没写明落点理由 |

清单本身每轮也查一遍（`verify_gates.check_root_tech_list`）：可加载、编号唯一、
每项都有切换信号、叶子落点都在分类表内、`RT:` 前缀常量没被改掉。战略相关度整维
都挂在这份清单上，清单坏了整维就静默失效。

## 5 接入点

| 环节 | 规则 |
|---|---|
| P1 宽召回 | **禁止**按根技术过滤。与根技术无关但技术价值高的事件仍可评 A，只是本项记 0 |
| P4 排序 | Strategic Adjacency 进入评级总分；同分时按 `priority`（P0 > P1 > P2）排序 |
| 第 1 章 | Dashboard 增加"按根技术方向分布"；每条主线写明推进了哪项根技术的哪个代际判断 |
| 第 5 章 | 命中候选根（B6.x）→ 记"候选根升格信号"；某 P0 根技术连续 N 轮无事件且覆盖面已证可达 → 记"根技术静默"（覆盖面不可达时记缺口，不记静默） |
| registry | 命题带根技术编号，跨轮次按根技术聚合，解决跨运行收敛无法记录的问题 |
| 必审清单 / 补检 | 由 `landing` 含"端侧/芯片/AgentOS"的 P0 根技术反推必查源组（如 M4.1 → 实时语音专项） |

## 6 编号冲突（必须处理）

根技术编号与 taxonomy 叶子编号 **有 11 处重名**：根技术 B1.1–B1.3、B2.1–B2.2、B3.1–B3.3、B4.1–B4.3 与叶子 B1.1 等完全同形，但含义无关（根技术 B1.1 = 个人媒体语料检索；叶子 B1.1 = 判断与动作选择）。

规则：**事件 JSON、卡片与第 7 章引用根技术一律写 `RT:` 前缀**（`RT:B1.1`），`leaves` / `primary_path` 字段只放裸叶子编号。门禁检查两者不混用。

## 8 回测暴露的三个清单缺口

以下事件技术价值明确，但在 82 项根技术里找不到归属。建议作为候选根提交下次半年复盘：

| 事件 | 问题 | 为何现有根不覆盖 |
|---|---|---|
| GPT-Rosalind-6（同权重 + 受信访问切出领域版本） | 领域专业化的实现位置从训练权重移到访问治理层 | B4.1 领域知识物化讲的是知识形态（符号/参数），不讲"谁能用、输出谁复核"；S1.2 任务级动态授权讲的是 Agent 动作权限，不讲模型准入 |
| Epoch：开源权重模型利用补丁窗口 | 开源模型进攻能力的成本拐点，以及由此产生的发布节奏约束 | M6.4 只测智能体任务能力，不测攻击能力；S2.2 讲供应链语义安全，不讲防守方的补丁发布节奏 |
| 四家共享 robots.txt 训练偏好信号 | 训练数据来源合规从单边声明转为跨厂商协议 | 清单里训练数据只出现在 M6.1（环境合成），没有"数据来源与授权"的根 |

前两项与终端厂商直接相关（领域模型准入、端侧补丁节奏），建议优先评估是否升格。
